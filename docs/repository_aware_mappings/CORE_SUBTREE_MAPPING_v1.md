# CORE SUBTREE MAPPING v1

Status: active canonical core-subtree mapping
Scope: repository-aware mapping for the core architectural layers
Rule: core-oriented subtrees must remain structurally explainable so foundational meaning does not dissolve into folder names alone

---

## 1. Purpose

This document defines the current repository-aware mapping for core-oriented subtrees.

It exists to preserve clarity about:
- where foundational platform meaning lives
- how core layers differ from downstream layers
- why core subtree identity matters for long-term continuity

---

## 2. Core Mapping Principle

Core-oriented repository areas should remain understandable in terms of:
- canonical models and contracts
- foundational rules
- bounded shared structural meaning
- non-UI and non-downstream identity

---

## 3. Mapping Intent

This mapping should help the operator or future engineer explain:
- which parts of the repo are foundational
- which parts define canonical structure
- why downstream layers must not silently become upstream truth owners

---

## 4. Required Rule

Core subtree interpretation should remain:
- explicit
- architecture-aware
- stable
- distinct from downstream runtime and presentation layers

---

## 5. What Is Forbidden

The following remain forbidden:
- core areas interpreted only by folder name guesswork
- downstream code silently treated as core authority
- core structure dissolved into generic project sprawl

---

## 6. Final Rule

The core subtree must remain structurally nameable and explainable if the platform is to remain coherent.

---

## 7. Status

This document is the active canonical core-subtree mapping until replaced by a stricter repository-aware architecture map.
