# CORE PROJECT MEMORY STRUCTURE v1

Status: active canonical project memory structure rule
Scope: what major memory/documentation domains must exist across the platform
Rule: project memory must be structured by domain so that continuity can be preserved at system scale

---

## 1. Purpose

This document defines the canonical memory structure of the project.

It exists to prevent:
- flat undocumented sprawl
- mixing unrelated rules into one place
- inability to recover project state from documentation

---

## 2. Required Core Memory Domains

The project memory structure should include domains such as:

- core architecture
- security/governance
- runtime/operations
- validation/testing
- observability/diagnostics
- visual/dashboard
- mobile/bridge/accelerator
- AI/memory/self-awareness
- agent/swarm
- runbooks/operator procedures
- release/change history

---

## 3. Required Principle

Each domain should preserve:
- concepts
- boundaries
- current rules
- continuity of decisions
- known debts or corrective passes when relevant

---

## 4. Continuity Rule

A future operator or future chat should be able to recover the major logic of the project from documentation and project memory without reconstructing everything from scratch.

---

## 5. Final Rule

Project memory must be structured, not improvised.

---

## 6. Status

This document is the active canonical project memory structure rule until replaced by a stricter continuity architecture standard.
