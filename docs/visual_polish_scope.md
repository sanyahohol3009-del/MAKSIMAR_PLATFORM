# VISUAL POLISH SCOPE v1

Status: active visual polish scope baseline  
Scope: allowed polish work after pre-polish gate is passed  
Rule: visual polish may improve clarity, depth, atmosphere, and coherence, but may not alter truth ownership or invent state

---

## 1. Purpose

This document defines what visual polish is allowed to do once the visual readiness gate has been passed.

It exists to prevent:

- polish turning into semantic redesign
- styling being used to hide unresolved logic
- fake “premium” visuals replacing evidence-backed interface behavior
- scope creep during the first polish phase

---

## 2. Core Principle

Visual polish is downstream refinement.

It may improve:

- clarity
- consistency
- depth
- hierarchy
- atmosphere
- readability
- operator confidence

It may not redefine:

- truth
- state meaning
- control flow
- policy meaning
- approval semantics
- runtime ownership

---

## 3. Allowed Polish Categories

## 3.1 Visual language refinement

Allowed:
- typography refinement
- spacing refinement
- alignment refinement
- border/radius consistency
- card chrome consistency
- icon consistency
- panel frame consistency

## 3.2 Premium HUD atmosphere refinement

Allowed:
- glow refinement
- glass refinement
- depth layering
- visual separation of zones
- controlled highlight emphasis
- refined status emphasis
- clearer center-core presentation

## 3.3 Structural visual coherence

Allowed:
- stronger left/center/right zoning
- stronger top-status and bottom-ticker coherence
- more consistent hierarchy between foundation/diagnostics/operator/topology surfaces
- improved panel grouping readability

## 3.4 Motion and effects refinement

Allowed later, if carefully controlled:
- subtle motion
- low-risk animation
- smooth transitions
- gentle pulse/glow behavior
- controlled signal flow animation
- optional core rotation capability

### Rule

Motion must remain subordinate to truth and readability.

---

## 4. Explicitly Allowed Project-Specific Visual Goals

The following polish goals are explicitly aligned with the current MAKSIMAR/JARVIS visual direction:

- dark premium operator HUD
- blue/orange accent system
- deep glass-like panel styling
- strong center-core visual gravity
- visible flow/signal routes around the core
- clear left navigation region
- clear right explainability/security region
- strong top status bar
- strong bottom status/ticker ribbon
- perceived depth in center/runtime/topology region

---

## 5. Forbidden Polish Behaviors

Polish must not:

- fabricate runtime activity
- fabricate trust/approval/health
- fake severity through decoration alone
- visually imply execution where none exists
- hide uncertainty behind style
- reduce explainability to decoration
- turn operator surfaces into cinematic noise
- make text less readable for atmosphere
- replace evidence with motion

---

## 6. Readability Rule

At all times, polish must preserve or improve:

- panel title readability
- status readability
- signal readability
- topology readability
- explainability readability
- alert readability

If a polish decision reduces readability, it fails.

---

## 7. Motion Rule

Motion is optional, never mandatory.

If motion is used, it must be:

- subtle
- traceable in purpose
- non-blocking
- non-deceptive
- low-noise
- readable under load

### Forbidden motion examples

- decorative chaos
- constant high-energy flicker
- fake “alive” movement without truth binding
- motion that masks state transitions
- motion that distracts from alerts or diagnostics

---

## 8. Center Core Rule

The center/core region may become visually stronger than the rest of the HUD, but it must remain truthful.

Allowed:
- stronger depth
- signal emphasis
- routing emphasis
- layered glow
- optional future controlled rotation capability

Forbidden:
- fake system activity
- fake execution pressure
- fake node load
- fake trust state

---

## 9. Sidebar Rule

The right explainability/security sidebar must remain explanation-first.

Polish may improve:
- framing
- emphasis
- typography
- separation
- visual trust

But it may not turn the sidebar into:
- vague flavor text
- ornamental filler
- ungrounded “AI wisdom”

---

## 10. Navigation Rule

The left navigation zone may be polished for:
- hierarchy clarity
- menu readability
- active-state clarity
- reduced clutter
- stronger operator confidence

But it must not become:
- hidden
- ambiguous
- overloaded with visual noise
- detached from actual panel/view structure

---

## 11. Panel Identity Rule

Polish may improve how panels look, but must not destroy panel identity.

This means:
- panel role differences should stay visible
- foundation vs diagnostics vs operator vs topology should remain distinguishable
- panel boundaries should remain traceable

---

## 12. First Polish Phase Scope

The first polish phase should be limited to:

- theme hardening
- spacing and hierarchy refinement
- card/frame coherence
- depth/glow discipline
- center-core refinement
- sidebar/navigation refinement
- ticker/status refinement

Not yet:
- major UX redesign
- advanced interaction redesign
- cinematic motion system
- complex multi-display choreography
- feature expansion disguised as polish

---

## 13. Operator Trust Rule

Every polish decision must improve operator trust, not merely visual excitement.

Good polish:
- reduces ambiguity
- increases confidence
- strengthens traceability
- improves signal-to-noise ratio

Bad polish:
- increases spectacle while reducing certainty

---

## 14. Final Rule

Polish must decorate truth, not compete with it.

If a visual decision makes the dashboard more beautiful but less honest, less clear, or less traceable, it is rejected.

---

## 15. Status

This document is the active baseline for allowed visual polish scope until replaced by a stricter visual language/polish standard.
