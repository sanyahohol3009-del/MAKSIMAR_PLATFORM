# 03 PRIMARY REENTRY SIGNAL RULE v1

Status: active_canonical
Document Type: canonical
Authority Level: operational
Interpretation Priority: high
Scope: rule for identifying the primary reentry signal across documentation packages
Rule: the primary reentry signal must remain readable so maintainers can orient from the strongest available cue before exploring deeper package detail

---

## 1. Purpose

This document defines the primary-reentry-signal rule of the platform.

It exists to preserve:
- readable first-orientation cues
- lower ambiguity around what signal matters most first
- continuity between package meaning and package reentry
- a stable base for later signal hardening

---

## 2. Priority Principle

Primary reentry signals should remain understandable in terms of:
- what cue should be read first
- why that cue has priority
- what it clarifies immediately
- how it reduces restart cost

---

## 3. Required Rule

Primary reentry signals should remain:
- explicit
- compact
- meaningful
- readable
- non-random

---

## 4. What Is Forbidden

The following remain forbidden:
- strongest reentry cue guessed only from memory
- primary signal buried inside weak details
- priority logic preserved only in operator memory
- restart that begins from arbitrary secondary signals

---

## 5. Final Rule

A mature documentation system defines the primary reentry signal before it widens restart depth.

---

## 6. Status

This document is the active canonical primary-reentry-signal rule until replaced by a stricter priority reference.
