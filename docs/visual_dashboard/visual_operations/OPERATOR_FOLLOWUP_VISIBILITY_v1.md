# OPERATOR FOLLOWUP VISIBILITY v1

Status: active canonical operator-followup visibility model
Scope: how visual/dashboard surfaces should support operator next-step thinking
Rule: dashboard visibility must remain useful for followup understanding rather than ending at passive display alone

---

## 1. Purpose

This document defines the operator followup visibility model of the platform.

It exists to preserve clarity about:
- why visibility alone is not enough
- how dashboard surfaces should help an operator think about next steps
- how runtime, health, and diagnostics visibility should remain actionable in understanding without becoming direct execution authority

---

## 2. Followup Visibility Principle

Dashboard visibility should not stop at “something is visible.”

It should support operator understanding of:
- what changed
- what state seems relevant
- whether deeper inspection is needed
- whether degraded or incident context matters
- how followup reasoning stays tied to upstream meaning

---

## 3. Required Rule

Followup visibility should remain:
- source-aware
- explainable
- downstream
- semantically bounded
- distinct from direct control authority

---

## 4. What Is Forbidden

The following remain forbidden:
- visibility that creates confusion but not understanding
- dashboard followup based only on guesswork
- visually intense output with no support for operator reasoning
- hidden transition from visibility to control behavior

---

## 5. Final Rule

A mature dashboard helps operators move from seeing to understanding, not from signal to confusion.

---

## 6. Status

This document is the active canonical operator-followup visibility model until replaced by a stricter operator-visibility reference.
